## Context

См. proposal.md — Why. Коротко о текущем состоянии: `get_next_movie_for_room` вызывает `_get_or_create_position`, который в create-ветке коммитит вставку строки позиции (position=0) **отдельно** от её продвижения (в конце метода). Между этими двумя commit-ами строка существует без блокировки, и параллельные запросы (предзагрузка фронта: 5 запросов на старте) читают позицию 0, отдают один и тот же фильм и пишут один и тот же advance — возникают дубликаты. Воспроизведено скриптом: 5 параллельных сессий → 3 уникальных фильма (стабильно).

## Goals / Non-Goals

Goals:
- Параллельные запросы «следующего фильма» возвращают разные фильмы, включая самые первые запросы участника (позиция не создана).
- Сохранить FOR UPDATE-сериализацию и существующую семантику пополнения/fallback.
- Тест, который воспроизводит гонку (текущий тест 6.2 её не ловит — идёт последовательно).

Non-Goals:
- Изменение схемы БД (миграции не нужны).
- Изменение frontend-предзагрузки (очередь из 5 запросов остаётся, это нагрузочная модель, на которой баг и проявился).
- Ручное пре-создание позиций при создании комнаты (вариант C) — не нужно.

## Decisions

### D1. Одна транзакция на insert + advance (вариант A)

В `_get_or_create_position` убрать `db.commit()` + `db.refresh()` из create-ветки. Вставка позиции остаётся незакоммиченной в сессии, и финальный `db.commit()` в `get_next_movie_for_room` персистит insert и продвижение (position = index + 1) **атомарно**.

Почему это закрывает гонку:
- INSERT строки неявно держит блокировку этой строки до конца транзакции победителя.
- Loser на `SELECT ... FOR UPDATE` / конкурентном INSERT незакоммиченную строку не видит: его INSERT блокируется до финального commit победителя, затем получает IntegrityError → `rollback` → `_get_position(lock=True)` читает уже продвинутую позицию (1, 2, …).
- Окно «строка есть, а advance ещё не сделан» исчезает: advance и insert коммитятся вместе.

Альтернативы:
- **B. `INSERT ... ON CONFLICT DO NOTHING RETURNING`** — тоже атомарен, но требует перехода на core-compiled upsert и меняет стиль остального кода (deck тоже создаётся вручную); выгода не оправдана.
- **C. Пре-создание позиций при создании комнаты** — убирает ленивое создание, но меняет жизненный цикл данных (нужна миграция/заполнение существующих комнат) — избыточно для фикса.

### D2. `_replenish_deck` не коммитит сам

Убрать внутренний `db.commit()` в `_replenish_deck` — он единственный вызов из `get_next_movie_for_room`, поэтому транзакционная граница остаётся за внешним методом. Это закрывает крайний случай: когда первый запрос участника попадает на уже исчерпанный колод, insert позиции и пополнение колода не разрываются промежуточным commit (иначе окно гонки вернулось бы на этой границе). FOR UPDATE на строку колода при этом держится до финального commit — безопасно, порядок блокировок одинаковый у всех запросов (позиция → колод), взаимных блокировок нет.

`_get_or_create_deck` не меняется: его create-commit происходит **до** создания позиции (порядок вызовов в `get_next_movie_for_room`), а сам колод общий на комнату — гонка курсора его не касается.

### D3. Тест гонки через барьер потоков

Новый тест в `test_shared_deck.py`: создать комнату с участником и ≥ N фильмами, **не** запрашивать фильм заранее (позиция не создана), затем N потоков (отдельные `SessionLocal`) одновременно вызывают `get_next_movie_for_room`, синхронизированных `threading.Barrier` непосредственно перед вызовом. Ассерт: N уникальных фильмов. Дубликаты в текущем коде воспроизводятся стабильно, так что тест детерминированно падает до фикса.

## Risks / Trade-offs

- [Транзакция держит блокировку строки позиции до финального commit] → Это и есть сериализация конкурентных предзагрузок; критично только на короткое время одного запроса (scan + возможно replenish). Взаимных блокировок нет (порядок «позиция → колод» одинаковый).
- [Loser блокируется на INSERT до завершения победителя] → Ожидаемое поведение: серия предзагрузок исполняется строго последовательно на уровне одной строки; для 5 запросов это микросекунды.
- [`_replenish_deck` без commit: любые изменения колода теперь коммитятся только в конце `get_next_movie_for_room`] → У метода единственный вызов; поведение с точки зрения наблюдателя не меняется (пак обновляется до возврата ответа).
- [Ранее закоммиченная строка позиции из другого запроса видна с неактуальной позицией при READ COMMITTED] → Не применимо после фикса: единственный путь создания строки — та же транзакция, что и advance.

## Migration Plan

- Схема не меняется: миграции не требуются.
- Развёртывание: перезапуск uvicorn (или авто-reload) после коммита фикса.
- Откат: revert коммита фикса — алгоритм вернётся к прежнему поведению; данные (строка позиции) не требуют очистки, продвижение корректируется следующими запросами.
