# Баг: «после запуска miniApp нужно 5 раз нажать лайк/дизлайк, чтобы карточка сменилась»

Документ — сводка всех известных фактов по багу, собранных в ходе расследования
12.08.2026. Содержит симптомы, хронологию, данные логов и БД, анализ кода,
подтверждённые причины, исправления и открытые вопросы.

---

## 1. Симптом

После запуска Telegram miniApp в комнате приложение показывает **один и тот же
фильм**, и требуется **5 нажатий** на лайк/дизлайк, чтобы карточка сменилась на
следующую. На бэкенд при этом уходят **5 одинаковых запросов** `POST /api/swipes/`
с одним и тем же `movie_id`, после каждого — `GET /api/movies/random`.

## 4. Анализ кода

### 4.1 Корневая причина №1 — гонка в `_get_or_create_position` (ИСПРАВЛЕНА)

`backend/app/services/deck_service.py`, метод `_get_or_create_position`
(старый код):

```python
position = self._get_position(db, user_id, room_code, lock=True)
if position:
    return position
position = RoomDeckPosition(...position=0)
db.add(position)
try:
    db.commit()          # ← гонка
except IntegrityError:
    db.rollback()
    position = self._get_position(db, user_id, room_code, lock=True)
    ...
```

**Механизм:** пока строка позиции (user, room) ещё не создана, `SELECT ... FOR
UPDATE` не на что блокироваться. 5 параллельных запросов (ровно столько делает
фронт при инициализации — `Promise.all` из 5 `getRandomMovie`):
- все 5 видят «позиции нет»;
- каждый вставляет свою строку и коммитит; проигравшие получают
  `IntegrityError` → `rollback` → читают **чужую** строку с `position=0`;
- все 5 сканируют колоду **с индекса 0** → все возвращают **один и тот же
  фильм** (deck[0]).

Итог: очередь фронта заполняется **5 одинаковыми фильмами** → карточка не
меняется 5 нажатий. Ровно «5», потому что фронт предзагружает 5 фильмов.

Триггер — **первый** запуск miniApp в комнате, где позиция ещё не создана.
При каждом новом коде комнаты (новая позиция) баг воспроизводится снова.

**Фикс (commit `43a2de0`, файл записан 11:47:41):**
- `db.commit() + db.refresh()` → `db.flush()` — вставка позиции остаётся
  незакоммиченной, строка держит блокировку до финального commit; конкурентный
  запрос блокируется на строке и после rollback читает уже продвинутую позицию;
- убран промежуточный `db.commit()` из `_replenish_deck`;
- `get_next_movie_for_room` закрывает транзакцию одним атомарным commit
  (insert позиции + advance + пополнение колоды).

**Проверка фикса:**
- новый регрессионный тест `test_parallel_first_requests_return_distinct_movies`
  (`backend/tests/test_shared_deck.py`): 5 потоков с отдельными `SessionLocal`,
  синхронизированных `threading.Barrier` перед вызовом → 5 уникальных фильмов;
- полный прогон: **16/16 passed**;
- repro-скрипт `/tmp/opencode/repro_deck_race.py` на исправленном коде:
  **5 запросов → 5 уникальных, дубликатов нет**.

### 4.2 Причина №2 — fallback `_random_movie` и исчерпание каталога (открыта)

`get_next_movie_for_room`: когда scan от позиции не находит фильм (всё
просвайпано) и пополнение не даёт новых фильмов, вызывается
`_random_movie(db)` — `SELECT ... ORDER BY func.random() LIMIT 1`. Этот путь
**не продвигает позицию** и возвращает **случайный** фильм из всех 100.

Следствия (для комнаты 99EXZL, где позиция застряла на 42):
- каждый `GET` возвращает случайный фильм без исключения ранее показанных;
- с вероятностью ~1/100 пара запросов может вернуть один и тот же фильм →
  в очереди фронта оказывается дубликат;
- именно этим объясняется дубль f9fcafdf на 11:33 (дважды, 4 с).

Это **не** даёт 5 одинаковых подряд (вероятность ~10⁻⁸), но даёт «мёртвые»
нажатия при единичных дублях.

Замечание: фильтр `_swiped_movie_ids` (`group_participants @> participants`)
захватывает и группу-супермножество `[25293232, 1472427136, 6136812654]` —
свайпы из другой комнаты «выжимают» каталог текущей (это ускоряет исчерпание).
Отмечено в докстрингах `_replenish_deck` как осознанное решение, но на 94/100
фильмов в комнате 99EXZL оно сыграло свою роль.

### 4.3 Причина №3 — фронтенд: `key={currentMovie.id}` при дубликате в очереди (усилитель)

`frontend/src/App.tsx:273`:

```tsx
<MovieCard key={currentMovie.id} movie={currentMovie} ... />
```

Если `next` из очереди имеет **тот же id**, что и текущий фильм, React видит тот
же ключ → `AnimatePresence` НЕ запускает exit-анимацию и НЕ перемонтирует
карточку → карточка визуально не меняется. Свайп при этом всё равно уходит на
бэкенд (`handleSwipe` отправляет `createSwipe` для текущего фильма). Пользователь
тапает снова → повторный свайп того же фильма → так, пока очередь не продвинется
до отличного фильма.

Т.е. **любой** дубликат в очереди превращается в «мёртвое» нажатие, а кластер
из N одинаковых → N мёртвых нажатий. Это усиливает и симптом №1, и №2.

## 5. Почему «ровно 5 нажатий»

Фронт при старте грузит **5 фильмов параллельно** (`App.tsx:132–138`), кладёт
первые 4 в очередь, 5-й показывает. При гонке №1 все 5 — один фильм:
текущий = X, очередь = [X, X, X, X]. Нажатия 1–4 «проходят» по X (карточка не
меняется из-за ключа), на 5-м очередь пуста → `loadMoreMovies()` → GET → новый
фильм. Отсюда **ровно 5**.

## 6. Что подтверждено / что остаётся не объяснённым

**Подтверждено:**
1. Гонка в `_get_or_create_position` (старый код) реально существует и даёт
   N одинаковых фильмов на N параллельных первых запросов — исправлена и
   покрыта тестом.
2. После фикса бэкенд (service-уровень) в том же сценарии возвращает
   5 уникальных фильмов.
3. Все пользовательские кластеры ×5 (03:58, 04:21, 11:43, 11:44) попали в логи
   **до** записи фикса (11:47) — на старом коде.
4. Комната 99EXZL с 03:57 находится в режиме постоянного fallback
   (случайный фильм, позиция не двигается).

**Не объяснено до конца:**
- Кластеры 04:21 и 11:43 произошли, когда позиция в 99EXZL уже существовала
  (42) → чистую гонку они объяснить не могут напрямую. Вероятные сценарии:
  (а) очередь фронта была загружена раньше, пока позиции не было (гонка), и
  дожила в WebView до момента свайпов; (б) использовались другие коды комнат
  (новые позиции → гонка), не 99EXZL. Ретроспективно однозначно установить
  невозможно.
- Точно не известно, перезагружался ли WebView Telegram между сессиями (кэш
  модулей по одинаковым URL; HMR Vite через ngrok не доходит).

## 8. Открытые вопросы / возможные доработки

1. **Fallback и исчерпание каталога:** `_random_movie` не исключает уже
   показанные фильмы и не продвигает позицию → повторные/случайные фильмы в
   режиме истощения. Стоит решить продуктово: например, исключать `swiped`
   и/или подмешивать повторы в конце, а не при каждом запросе.
2. **Фронтенд:** защититься от дубликатов в очереди (skip-попап с повторяющимся
   id, либо ключ карточки не по id) — тогда даже случайный дубль из fallback
   не даст «мёртвого» нажатия.
3. **Фильтр групп:** `@>` по составу участников захватывает группы-супермножества
   → свайпы из других комнат выжимают каталог текущей.
4. **Инструментарий:** логгровать путь выдачи (deck vs replenish vs fallback) и
   id фильма в `GET /api/movies/random`, чтобы отличать fallback-повторы от
   настоящих гонок по логам.
