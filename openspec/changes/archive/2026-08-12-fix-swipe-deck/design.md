## Context

См. proposal.md — Why. Ключевое текущее состояние: `RoomDeck` (`backend/app/models/room_deck.py`) хранит только упорядоченный `movie_ids` (JSONB), позиции участников нет. `deck_service.get_next_movie_for_room` всегда возвращает первый непросвайпнутый фильм и не продвигает позицию при выдаче, поэтому параллельные запросы предзагрузки фронта (`frontend/src/App.tsx`, `Promise.all` из 5 `getRandomMovie`) возвращают один и тот же фильм. Карточка рендерится по `key={currentMovie.id}` — одинаковый `id` не пересоздаёт карточку, очередь из 5 одинаковых копий исчерпывается → «Нет доступных фильмов».

## Goals / Non-Goals

**Goals:**
- Каждый запрос «следующий фильм комнаты» продвигает позицию участника и возвращает следующий по общему колоду фильм.
- Несколько параллельных запросов (предзагрузка) от одного участника возвращают разные фильмы без повторов.
- Карточка и скелетон адаптивно заполняют свайп-область с сохранением пропорции 2:3.
- При исчерпании предзагруженной очереди показывается скелетон/догрузка вместо мгновенной заглушки «Нет доступных фильмов».

**Non-Goals:**
- Не меняем контракт `GET /api/movies/random` (заголовки `telegram-id`, query `room_code`, формат ответа).
- Не трогаем свайп-анимации и обработку жестов (это покрыто change `swipe-ux`).
- Не реализуем персонализированную систему просмотренных фильмов (TODO из `movie_service.py`).

## Decisions

### D1. Курсор участника хранится в новой таблице `room_deck_positions`

Новая модель `RoomDeckPosition` с композитным PK `(user_id, room_code)` и полем `position` (индекс в `movie_ids`). При первом запросе участника строка создаётся с `position = 0`.

- **Почему таблица, а не колонка в `RoomDeck`**: позиция per user+room, колонок в общем колоде было бы N участников — не масштабируется и не соответствует «независимому движению».
- **Альтернатива (отклонена)**: выводить позицию из свайпов — ненадёжно, т.к. предзагрузка опережает свайпы и позиция не может быть восстановлена из фактов свайпов.

### D2. Сериализация параллельных запросов — row lock на строку позиции

Чтение/продвижение позиции выполняется в одной транзакции с `SELECT ... FOR UPDATE` на строку `room_deck_positions`. 5 параллельных предзагрузок одного участника сериализуются и получают разные фильмы. Создание строки при гонке — как у `_get_or_create_deck`: `IntegrityError` → `rollback` → повторный `SELECT ... FOR UPDATE`.

- **Почему lock на позицию, а не на колод**: блокировка колода сериализовала бы всех участников комнаты; lock на позицию сериализует только запросы одного участника, что соответствует независимому движению.

### D3. Логика выдачи: prune → clamp → scan → advance

Алгоритм `get_next_movie_for_room` с курсором:
1. Взять колод (создать при необходимости) и строку позиции (создать при необходимости, с lock).
2. **Prune**: убрать из `movie_ids` удалённые фильмы (ротация) — как сейчас в `_first_available_in_deck`, с сохранением в БД.
3. **Clamp**: `position = min(position, len(movie_ids))`.
4. **Scan**: пройти `movie_ids[position:]`, пропуская уже просвайпанные участником в этой комнате.
5. Если дошли до конца без результата — пополнить колод (существующий `_replenish_deck`) и продолжить scan.
6. Если фильм найден — установить `position = index_found + 1`, сохранить, вернуть фильм. Иначе `None`.

- **Почему prune до clamp**: после удаления фильмов индексы сдвигаются; простая коррекция — не хранить `movie_id` последнего показанного, а ограничиться clamp и пропуском вперёд. Гарантия «без повторов» не ломается: каждый запрос всегда продвигает позицию вперёд, повторов фильмов для участника нет; возможный сдвиг индекса после ротации лишь «пропускает вперёд» — приемлемо и фиксируется как trade-off.
- `_swiped_movie_ids_in_room` для пополнения колода остаётся как есть.

### D4. Карточка: размер от высоты области, а не от `max-w-md`

В `MovieCard.tsx` и `SkeletonCard.tsx` заменить `w-full max-w-md aspect-[2/3] max-h-full` на размер, производный от высоты: `h-full aspect-[2/3] max-w-full` (ширина вычисляется из высоты через `aspect-ratio`; `max-w-full` страхует узкие экраны). Обёртка `absolute inset-0 flex items-center justify-center p-4` сохраняется.

- **Почему от высоты**: у свайп-области высота определена (flex-цепочка из фикса layout), и именно она «узкое место» на телефоне; `max-h-full` ломает `aspect-ratio` (сплющивание), а `max-w-md` душит карточку на широких экранах.
- **Альтернатива (отклонена)**: `width: min(100%, calc((100dvh - offset) * 2/3))` — хрупко, зависит от отступов/баннеров.

### D5. Догрузка очереди без заглушки

В `handleSwipe` при исчерпании очереди показывать `SkeletonCard` (флаг загрузки следующего фильма) вместо немедленного блока «Нет доступных фильмов». Заглушка остаётся только если догрузка реально вернула пусто (`None`/ошибку).

## Risks / Trade-offs

- **Сдвиг позиции при ротации/пополнении** → Позиция может «перескочить вперёд» (участник увидит фильм чуть позже, чем без ротации). Повторов не возникает; компенсируется clamp и prune-перед-scan. → Mitigation: документировать в коде; сценарий покрыт тестом.
- **Гонка параллельных запросов** → Дубликаты фильмов в предзагрузке. → Mitigation: `SELECT ... FOR UPDATE` + обработка `IntegrityError` при создании строки позиции; тест на 5 параллельных вызовов.
- **`aspect-ratio` в старых WebView Telegram (iOS < 15)** → Свойство не поддерживается, карточка получит `height:100%` без расчёта ширины. → Mitigation: современный `aspect-ratio` поддерживается в актуальных Telegram-клиентах; как fallback допустимо сохранить прежний размер по ширине.
- **Дополнительный round-trip к БД на запрос** → Одна блокирующая запись позиции на запрос фильма. → Mitigation: масштаб комнат мал, влияние незначительное.

## Migration Plan

1. Alembic-ревизия: создание таблицы `room_deck_positions` (FK на `users.id`, `rooms.id`, CASCADE).
2. Деплой: новая таблица пустая — первый запрос участника создаёт строку `position = 0`, старое поведение эквивалентно начальному. Старые колоды не меняются.
3. Rollback: откат ревизии (drop таблицы) — старый код (первый непросвайпнутый) продолжает работать, контракт API не меняется. Фронтенд — статика, откат = передеплой предыдущего билда.
