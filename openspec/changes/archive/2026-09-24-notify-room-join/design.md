## Context

Присоединение к комнате обрабатывается только в `RoomService.join_room` (`backend/app/services/room_service.py`), вызывается только из бот-хендлера `join_room` (`backend/app/bot/handlers.py`). API (`backend/app/api/rooms.py`) присоединение не реализует — только чтение. Уже есть рабочий паттерн фоновой Telegram-рассылки в `notification_service.send_match_notification`: он извлекает из ORM-объектов чистые данные до старта фонового потока, поднимает свой event loop в отдельном треде и шлёт сообщения каждому получателю в своём `try/except`, чтобы одна ошибка не блокировала остальных. См. proposal.md - Why.

## Goals / Non-Goals

**Goals:**
- Переиспользовать существующий паттерн фоновой асинхронной отправки уведомлений (`notification_service`), а не изобретать новый механизм.
- Гарантировать, что рассылка уведомлений не блокирует и не может сломать ответ пользователю, присоединившемуся к комнате, и не влияет на транзакцию `join_room`.
- Безопасно обращаться с непроверенными именами/юзернеймами участников (только plain text, без `parse_mode`).

**Non-Goals:**
- Не добавляется join через API/Mini App — присоединение остаётся бот-командой.
- Не вводится персистентная очередь уведомлений или ретраи с бэкоффом — поведение при ошибке отправки одному получателю аналогично `send_match_notification` (залогировать и продолжить).
- Не меняется формат/поведение `/room_info` — эта команда остаётся как есть.

## Decisions

- **Хук — сразу после `db.commit()`/`db.refresh(room)` в `RoomService.join_room`.** Альтернатива — вызывать уведомление из бот-хендлера `handlers.join_room` после успешного вызова сервиса. Выбран сервисный слой, так как это единственная точка присоединения и по правилам проекта бизнес-логика (включая триггер уведомления) должна жить в `services/`, а не в тонком хендлере бота.
- **Новый метод `notification_service.send_room_join_notification(room, joined_user, db)`**, реализованный по образцу `send_match_notification`: синхронная точка входа, которая забирает нужные данные (список `telegram_id` остальных участников, имя присоединившегося, код комнаты, итоговое число участников) из ORM-объектов *до* запуска фонового потока, затем `threading.Thread(target=run_async, daemon=True).start()` с собственным `asyncio` event loop внутри. Альтернатива — переиспользовать `_send_match_notification_async`, обобщив под произвольный текст, но это смешало бы разные предметные события (матч vs. присоединение) в одной функции; отдельный метод проще читать и тестировать.
- **Получатели — все участники комнаты, кроме только что присоединившегося**, вычисляются как `[tid for tid in room.participants if tid != joined_user.telegram_id]`. Если список пуст (первый участник в новой комнате), уведомление не отправляется вовсе — не создаём фоновый поток без получателей.
- **Текст сообщения — только plain text**, аналогично недавнему фиксу `/room_info` (commit `faaec58`): имя/username пользователя не экранируются под Markdown, поэтому `parse_mode` не используется.
- **Ошибки уведомления не влияют на `join_room`.** Вызов оборачивается в `try/except Exception` с `logger.error(..., exc_info=True)` в самом сервисе, аналогично тому, как `match_service.create_match` оборачивает вызов `send_match_notification` — присоединение к комнате должно оставаться успешным, даже если Telegram недоступен или уведомление не удалось запустить.

## Risks / Trade-offs

- [Фоновый поток на каждое присоединение] → при частых одновременных присоединениях создаётся несколько daemon-тредов со своими event loop, как и для матчей; при текущем масштабе (комнаты до 5 участников) это приемлемо и не требует пула потоков.
- [Гонка: пользователь присоединяется, пока другой участник уже видит устаревший список] → уведомление формируется из `room.participants` сразу после `commit`/`refresh`, то есть отражает актуальное состояние на момент присоединения; более поздние изменения состава не влияют на уже отправленное уведомление.
- [`notification_service.bot is None` в тестах/при отсутствии токена] → метод должен молча не отправлять сообщения (как и существующий `send_match_notification`), не бросая исключение.
