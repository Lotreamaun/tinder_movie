## Context

См. proposal.md - Why. Технический контекст, важный для решения:

- `deck_service.get_next_movie_for_room` держит `FOR UPDATE` на строках `room_decks` и `room_deck_positions` в течение ОДНОЙ транзакции с единственным финальным `db.commit()` (инвариант D1/D2, закреплённый фиксом гонки `43a2de0` и `design.md` change `fix-parallel-preload-duplicates`). Любой промежуточный commit или долгая операция внутри этой транзакции возвращает риски, которые тот фикс устранял: удержание блокировок дольше необходимого блокирует параллельные запросы того же участника и других участников комнаты.
- `movie_service.load_batch_movies` делает сетевые HTTP-запросы к Kinopoisk и коммитит **после каждого фильма** (`create_movie` → `db.commit()`), т.е. не совместим с инвариантом «один финальный commit» деки, если вызывать его на той же сессии/транзакции.
- `MAX_MOVIES_IN_DB = 100` и `cleanup_old_movies` сегодня недостижимы в комнатном флоу (см. proposal) — этот change их не включает в комнатный путь, а оставляет как есть для нерумного флоу и ручного скрипта.
- **Подтверждено ручной проверкой (task 5.1) первой версии фикса**: `load_batch_movies` грузит фильмы по одному отдельным HTTP-запросом (`fetch_movie_from_kinopoisk`); догрузка 30 фильмов заняла ~88 секунд в реальном прогоне. Фронтенд (`frontend/src/services/api.ts:89`) ставит `axios` таймаут 10 секунд. Синхронный вызов догрузки внутри `get_next_movie_for_room` (даже на отдельной сессии, без нарушения инварианта FOR UPDATE) всё равно держит HTTP-соединение с фронтендом открытым дольше его таймаута — пользователь получает ошибку, хотя бэкенд успешно завершает работу. Это и есть причина пересмотра Decision 1 ниже.
- **Выявлено ручной проверкой (task 9.1):** `get_top_movies_from_kinopoisk` для каждого фильма страницы топа делает отдельный запрос полных данных — **до** того, как `load_batch_movies` проверит, есть ли фильм в БД; каждая догрузка начинает со страницы 1. Страница из 20 уже известных фильмов стоит 21 запрос, пустая догрузка (до 10 страниц) — ~210. На практике дневная квота (500) была исчерпана за несколько догрузок (`402 … 530 request, but available 500 per day`), после чего догрузка перезапускалась на каждом запросе: in-process guard запрещает только параллельный запуск, но не повторный сразу после неудачи.
- `UserSwipe.group_participants` — JSONB-массив участников комнаты на момент свайпа; сопоставление со «свайпан ли фильм для комнаты» идёт через `@>` (contains), без ограничения по времени — свайп исключает фильм из показа навсегда, пока состав участников не изменится.

## Goals / Non-Goals

**Goals:**
- Комнатный флоу реально запускает догрузку каталога из Kinopoisk, когда у участника остаётся мало непросвайпанных (в текущей сессии) фильмов — **проактивно**, до полного исчерпания.
- Догрузка каталога не нарушает инвариант «один финальный commit», не держит `FOR UPDATE` во время сетевого запроса к Kinopoisk, и **не блокирует HTTP-ответ** текущего запроса (см. риск таймаута фронта выше).
- Финальный fallback (`_random_movie`) по возможности не повторяет фильмы, уже просвайпанные участником в комнате **в рамках текущей сессии**.
- Просвайпанность фильма не действует бессрочно: комната, которой пользуются неделями, не должна упираться в вечное исключение всего каталога — вводится скользящая 24-часовая сессия активности группы.
- Матч учитывает только лайки текущей (не истёкшей) сессии; уже созданные матчи не аннулируются задним числом при истечении сессии.
- Путь выдачи фильма (deck / replenished-from-catalog / random-fallback) и факт запуска фоновой догрузки логируются для будущей диагностики.

**Non-Goals:**
- Периодическая догрузка по расписанию (cron, APScheduler), независимая от запросов пользователей, — по-прежнему вне рамок. В рамках этого change догрузка остаётся *триггеримой запросом* (по порогу непросвайпанных фильмов), но теперь **выполняется в фоновом потоке**, не блокируя ответ на вызвавший её запрос — это не периодика, а асинхронное выполнение уже принятого решения.
- Явное хранимое поле сессии (`session_started_at`/`last_activity_at` в `rooms` или отдельной таблице) — рассмотрено и отклонено в пользу вычисления на лету (Decision «Сессия» ниже); не требует Alembic-миграции.
- Синхронизация фоновой догрузки между несколькими процессами/воркерами (Redis-лок, advisory lock в Postgres и т.п.) — вне рамок; используется простой in-process guard, текущий деплой — один процесс `uvicorn` без `gunicorn`/нескольких воркеров.
- Ретроактивное удаление/аннулирование уже созданных записей в `matches` при истечении сессии — не делаем; история матчей и отправленные уведомления сохраняются, сброс сессии влияет только на будущие вычисления.
- Пересмотр `MAX_MOVIES_IN_DB` / включение `cleanup_old_movies` в комнатный флоу — не делаем: cleanup сегодня не участвует в комнатном пути, и включать его заодно с ростом каталога — отдельное решение с своими рисками (удаление фильмов, ещё нужных активным колодам комнат). Помечено открытым вопросом.
- Дубли в очереди предзагрузки фронта (склейка одинаковых параллельных GET, `Cache-Control: no-store`, дедуп очереди по id) — относится к `fix-parallel-preload-duplicates`, не входит в этот change.
- Фильтр `group_participants @>` (свайпы из комнаты-надмножества съедают каталог текущей) — отдельная, уже задокументированная причина (`fix-parallel-preload-duplicates/bug-investigation.md`, п.8.3), не входит в этот change.

## Decisions

### 1. Догрузка каталога — фоновый поток, отдельная сессия, не блокирует ответ

Когда у участника остаётся меньше `DECK_CATALOG_LOW_THRESHOLD` (= 30, см. Risks про выбор числа) непросвайпанных **в текущей сессии** (Decision 5) фильмов, и фоновая догрузка ещё не идёт (in-process guard), `deck_service` запускает `movie_service.load_batch_movies` в **фоновом потоке** (`threading.Thread(..., daemon=True).start()`), на **отдельной `SessionLocal()`**, независимой от локальной транзакции с `FOR UPDATE` на deck/position. Текущий запрос **не ждёт** результата — продолжает штатный путь (scan → replenish-from-catalog → random-fallback) и возвращает ответ немедленно. После того как фоновый поток закоммитил новые фильмы, следующий запрос (этого или другого участника) увидит их через обычный `_replenish_deck` (`replenished-from-catalog`).

Это пересмотр решения из первой версии change: там догрузка была синхронной (тоже на отдельной сессии, вне `FOR UPDATE`), но вызывалась и ожидалась **внутри того же HTTP-запроса**. Ручная проверка (task 5.1, см. Context) показала, что это всё равно ломает UX — фронтенд обрывает запрос по таймауту 10с задолго до того, как Kinopoisk успевает ответить (~88с на 30 фильмов).

In-process guard: простой `threading.Lock` + флаг «догрузка уже идёт» в `deck_service`, проверяется неблокирующим образом (`acquire(blocking=False)` или эквивалент) перед стартом потока; снимается в `finally` фонового задания. Гарантирует, что параллельные запросы разных участников, одновременно пересёкшие порог, не запустят несколько одновременных догрузок (расход лимита Kinopoisk API). Не защищает от дублирования между несколькими процессами/воркерами (см. Non-Goals) — приемлемо для текущего однопроцессного деплоя.

Альтернатива (отклонена, была принята в первой версии change): ждать результат догрузки внутри текущего запроса. Отклонено по итогам ручной проверки — см. выше.

Альтернатива (отклонена): вызывать `load_batch_movies` прямо на текущей `db`-сессии. Отклонено, потому что `load_batch_movies` коммитит на каждый фильм — это ломает инвариант единственного финального commit деки (риск регрессии гонки, исправленной в `43a2de0`) и держит `FOR UPDATE` на deck/position на время нескольких HTTP-запросов к Kinopoisk, блокируя остальных участников комнаты.

Альтернатива (отклонена): вернуть общую проверку `MOVIES_LOAD_THRESHOLD` в начало `movie_service.get_random_movie` без раннего return для комнатного флоу. Отклонено — это запускало бы обращение к Kinopoisk на КАЖДЫЙ запрос, пока общий счётчик каталога ниже порога, независимо от остатка у конкретного участника.

### 2. Место триггера — сразу после вычисления `swiped`, до scan

`get_next_movie_for_room`: сразу после вычисления session-aware `swiped` (Decision 5) — до scan колода — считается остаток непросвайпанных фильмов участника; если он меньше порога, запускается фоновая догрузка (Decision 1), не блокируя дальнейшее выполнение. Дальше выполняется прежняя цепочка: scan текущего колода → `_replenish_deck` из существующего каталога → `_random_movie` (исключая session-aware `swiped`). Путь `replenished-after-fetch` (внутри одного запроса) исчезает — догрузка больше никогда не завершается в рамках вызвавшего её запроса.

### 3. `_random_movie` исключает свайпы участника текущей сессии, когда это возможно

`_random_movie` получает уже вычисленный session-aware `swiped` (набор movie_id, просвайпанных этим участником в комнате **в рамках текущей сессии**) и исключает их из выборки (`WHERE id NOT IN (...)`), если после исключения остаётся хотя бы один фильм. Если множество `swiped` покрывает весь каталог — исключение снимается (иначе `_random_movie` вернёт `None`, и фид оборвётся, что хуже повтора).

### 4. Логирование

Каждый возврат из `get_next_movie_for_room` логирует один из путей: `deck` (обычный scan), `replenished-from-catalog`, `random-fallback`. Отдельной строкой логируется запуск фоновой догрузки (`room_code`, `user_id`, остаток фильмов) и, при истечении сессии, сам факт сброса (`room_code`, сколько времени простоя). 402 от Kinopoisk (исчерпана квота) — ожидаемая ситуация, а не ошибка кода: логируется одной строкой `WARNING` без traceback; постановка паузы догрузки (Decision 8) — тоже одной строкой.

### 5. Сессия — скользящее 24-часовое окно, вычисляется на лету

«Просвайпанность» фильма для целей исключения (колод, пополнение, `_random_movie`) и для проверки матча (`swipe_service.check_match`) учитывает только свайпы **текущей сессии комнаты**. Сессия определяется по истории `user_swipes`, отфильтрованной по группе участников (`group_participants @>`, та же семантика, что уже используется):

- Если с последнего свайпа ЛЮБОГО участника группы прошло ≥24 часов (или свайпов не было вовсе) — текущая сессия пуста: ни один прошлый свайп не считается «показанным», следующий свайп начинает новую сессию.
- Иначе `session_start` — момент начала текущей непрерывной серии свайпов: последняя точка разрыва ≥24ч между соседними свайпами группы (или самый первый свайп, если разрывов не было). Вычисляется одним SQL-запросом с оконной функцией:

  ```sql
  WITH group_swipes AS (
      SELECT swiped_at,
             LAG(swiped_at) OVER (ORDER BY swiped_at) AS prev_swiped_at
      FROM user_swipes
      WHERE group_participants @> :participants
  )
  SELECT MAX(swiped_at) AS session_start
  FROM group_swipes
  WHERE prev_swiped_at IS NULL OR swiped_at - prev_swiped_at >= interval '24 hours';
  ```

- Все читающие запросы (`_swiped_movie_ids`, `_swiped_movie_ids_in_room`, `swipe_service.check_match`) добавляют условие `swiped_at >= session_start` (или дают пустой результат, если сессия пуста per правило выше).
- `create_swipe`/`get_swipe` **не меняются**: идемпотентность по-прежнему ищет существующую запись без ограничения по времени и обновляет её `swiped_at`/`swipe_type`. Это специально: повторный свайп фильма из истёкшей сессии естественным образом «переносит» его в новую сессию (его `swiped_at` становится текущим), без дублирования строк.
- Уже созданные записи в `matches` не удаляются и не инвалидируются при истечении сессии (Non-Goals) — сброс влияет только на будущие вычисления исключений и новых матчей.

Альтернатива (отклонена): хранить `session_started_at`/`last_activity_at` явным полем в `rooms` (или отдельной таблице), обновляемым при каждом свайпе. Быстрее читать (без window-функции на каждый запрос), но требует Alembic-миграции и кода поддержания консистентности состояния при каждом свайпе (риск рассинхронизации при гонках/ошибках). Отклонено в пользу вычисления на лету ради простоты (KISS) и отсутствия побочного состояния; если объём `user_swipes` на комнату станет проблемой для производительности — можно пересмотреть отдельным change.

### 6. Пополнение колода «рециклом» после исчерпания новых фильмов

Сброс сессии (Decision 5) сам по себе не возвращает старые фильмы в **общий** порядок: курсоры участников уже стоят в конце колода, а `_replenish_deck` исключает всё, что уже есть в колоде. После сброса старые фильмы доставались бы только через `random-fallback` — независимо для каждого участника, и общий матч на них был бы практически недостижим. (Найдено при реализации разделов 6–8.)

Поэтому `_replenish_deck` работает в два этапа:

1. **Новые фильмы** (как раньше): фильмы каталога, которых ещё нет в колоде и которые не просвайпаны участником в текущей сессии. Приоритет — свежему контенту.
2. **Рецикл**, если этап 1 ничего не дал: фильмы, не просвайпанные участником в текущей сессии, **кроме** последних `DECK_BATCH_SIZE` элементов колода перед курсором участника. Они дописываются в конец общего колода — остальные участники увидят их в том же порядке, матч снова достижим.

Окно `DECK_BATCH_SIZE` перед курсором — защита от дублей предзагрузки (change `fix-parallel-preload-duplicates`): фронтенд держит очередь из нескольких уже выданных, но ещё не свайпнутых фильмов; без окна они вернулись бы в колод и показались повторно.

Следствие: колод может содержать один фильм несколько раз (в разных «кругах»). Это безопасно — scan пропускает просвайпанные в текущей сессии фильмы, а курсор монотонен.

Альтернатива (отклонена): при истечении сессии сбрасывать колод и курсоры комнаты. Требует записи в БД под блокировками при обнаружении истечения и добавляет гонки между участниками; рецикл решает ту же задачу без нового состояния.

### 7. Догрузка не запрашивает данные известных фильмов

`get_top_movies_from_kinopoisk` проверяет `kinopoisk_id` каждого фильма страницы топа по БД **до** запроса полных данных и пропускает уже существующие. Страница, где все фильмы известны, стоит 1 запрос вместо 21. Пагинация по-прежнему с первой страницы: в топе ~13 страниц, так что полный проход по известным страницам стоит ≤13 запросов.

Важно: страница, где все фильмы уже известны, отдаёт **пустой список кандидатов**, но это не конец пагинации — `load_batch_movies` обязан пойти на следующую страницу. Чтобы отличить «страница была, но всё известно» от «Kinopoisk больше не отдаёт страниц» (реальный конец, нет ключа, ошибка запроса), `get_top_movies_from_kinopoisk` возвращает `None` только во втором случае; пустой список (`[]`) — валидный сигнал «страница обработана, кандидатов нет, продолжай». Найдено и исправлено ручной проверкой (task 9.1, повторный прогон): без этого различия `load_batch_movies` останавливался на первой же полностью известной странице, и догрузка почти никогда не находила новых фильмов, несмотря на то что они были дальше в топе.

Альтернатива (отклонена): запоминать номер последней обработанной страницы. Лишнее хранимое состояние, пропускает новые фильмы при сдвиге топа, а после проверки по БД выигрыш — единицы запросов.

### 8. Пауза после пустой или неудачной догрузки

Если `_grow_catalog` вернул 0 или упал с исключением, `deck_service` запоминает момент `now + CATALOG_GROWTH_COOLDOWN_MINUTES` (по умолчанию 30); до него `_maybe_grow_catalog` фоновую догрузку не запускает. Успешная догрузка (>0 фильмов) паузу не ставит. Состояние хранится в памяти процесса, как и in-process guard (Decision 1), и сбрасывается при рестарте — приемлемо для однопроцессного деплоя. Фид при этом не страдает: ответ идёт штатным путём (deck → рецикл → random-fallback).

## Risks / Trade-offs

- **[Риск] Порог 30 подобран с запасом, но не гарантирует отсутствия повторов.** При ~88с на догрузку 30 фильмов участник, свайпающий быстрее ~3с/фильм, теоретически может обогнать фоновую догрузку и на короткое время получить `random-fallback` (повтор) до её завершения. → Осознанный компромисс: это временно и на порядок реже/короче, чем прежний блокирующий вызов; после завершения фоновой догрузки повторы снова становятся редкими. Число 30 можно тюнинговать по факту наблюдений.
- **[Риск] `KINOPOISK_API_KEY` не задан или исчерпан лимит.** `load_batch_movies`/`get_top_movies_from_kinopoisk` в этом случае просто возвращают 0 — деградация до текущего поведения (fallback на повтор), не хуже, чем сейчас; с Decision 8 пустые попытки повторяются не чаще раза в `CATALOG_GROWTH_COOLDOWN_MINUTES`.
- **[Риск] Источник `TOP_250_BEST_FILMS` почти выбран.** В каталоге уже ~195 из ~250 фильмов; вскоре догрузка будет стабильно пустой, и фид будет держаться на рецикле и сбросах сессии. → Расширение источника — Open Question ниже.
- **[Риск] Неограниченный рост каталога.** Без `cleanup_old_movies` в комнатном флоу (Non-Goal) каталог будет расти без верхней границы, пока где-то не запускается ручной скрипт или не задействован нерумный путь. → Это осознанный компромисс для этого change; отмечено открытым вопросом ниже.
- **[Риск] Window-функция на каждый запрос.** Вычисление `session_start` выполняется на каждый вызов `get_next_movie_for_room`/`check_match`. → Запрос ограничен историей ОДНОЙ комнаты (`group_participants @>`), объём для реального использования (недели/месяцы одной комнатой) остаётся небольшим; при заметной деградации производительности — см. Decision 5, отклонённая альтернатива.
- **[Риск] In-process guard не работает между процессами.** При деплое с несколькими воркерами (`gunicorn -w N` и т.п.) каждый процесс может параллельно запустить свою догрузку при одновременном пересечении порога участниками разных запросов. → Текущий деплой — один процесс; при масштабировании потребуется общий (Redis/DB advisory lock) guard — вне рамок этого change.

- **[Риск] Колод растёт с повторами при рецикле.** Каждый круг рецикла дописывает до `DECK_BATCH_SIZE` фильмов. → Рост линеен по числу выдач и ограничен активностью комнаты; при необходимости — компакция колода отдельным change.

## Migration Plan

Изменения только в поведении сервисов (`deck_service.py`, `swipe_service.py`, `movie_service.py`) и в конфиге (`config.py`, новый порог), без изменений схемы БД — новой Alembic-миграции не требуется (сессия вычисляется на лету, Decision 5). Раскатывается обычным деплоем backend; откат — предыдущей версией кода, данные (уже загруженные фильмы, свайпы) не требуют отката.

## Open Questions

- Нужно ли поднять/убрать `MAX_MOVIES_IN_DB` и включить `cleanup_old_movies` в комнатный флоу теперь, когда каталог реально растёт через Kinopoisk? Можно отложить до отдельного change, если рост каталога на практике останется умеренным.
- Стоит ли расширять источник фильмов за пределы `TOP_250_BEST_FILMS` (Kinopoisk предоставляет другие типы подборок) — при долгом использовании одной комнаты (недели/месяцы) даже со сбросом сессии каждые 24ч простоя источник в ~250 фильмов конечен, и участники рано или поздно увидят все. Не входит в этот change.
