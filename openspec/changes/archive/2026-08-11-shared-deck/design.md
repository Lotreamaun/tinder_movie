## Context

Текущее поведение: `GET /api/movies/random` (`movie_service.get_random_movie`) отдаёт случайный фильм из общей базы каждому запрашивающему. У комнат нет общего состояния — участники почти никогда не видят один фильм, поэтому свайп-матч («все лайкнули один фильм») практически невозможен. Существующие данные: `user_swipes` уже хранит `(user_id, movie_id, group_participants, swipe_type)`; `rooms` хранит `participants` (JSON telegram_id). Наполнение базы фильмами — фоновый процесс (см. change `deploy-readiness`).

## Goals / Non-Goals

**Goals:**
- Общая упорядоченная последовательность фильмов на комнату.
- Каждый участник движется по колоду в своём темпе, без повторов для себя.
- Автопополнение колода при исчерпании; устойчивость к удалению фильмов.
- Матч становится достижимым в комнате.

**Non-Goals:**
- Персонализация/рекомендации (TODO в `movie_service` остаётся вне скоупа).
- Жёсткая синхронизация участников (все видят строго deck[i] одновременно — не требуется).
- Качество/курирование наполнения колода.

## Decisions

### 1. Модель данных: таблица `room_decks`

- Новая таблица `room_decks`: `room_code` (PK, FK→rooms.id, ondelete CASCADE), `movie_ids` (JSONB — упорядоченный массив UUID фильмов), `created_at`.
- Персональные позиции **не хранятся**: «следующий фильм участника» вычисляется по колоду минус его свайпы в этой комнате.
- **Почему не позиция-счётчик на пользователя**: потребовались бы записи/синхронизация при каждом запросе; join по уже существующим свайпам — read-only, идемпотентно и использует текущие данные. Для колода ≤ ~100 фильмов запрос дёшев.
- **Альтернативы**: поле-колод на самой комнате (смешивает жизненный цикл комнаты и дек, мешает пересоздавать колод); отдельная таблица `user_deck_positions` (лишние записи и конкурентные апдейты). Выбрана `room_decks`.

### 2. Выдача следующего фильма

- Эндпоинт `GET /api/movies/random` получает контекст комнаты (query-параметр `room_code`, сверяется с проверенной личностью — см. `deploy-readiness`).
- Логика: взять колод комнаты; выбрать первый `movie_id`, который (a) существует в `movies`, (b) не свайпнут этим пользователем в этой комнате (anti-join `user_swipes` по `user_id` + `movie_id`). Если такого нет — пополнить колод и повторить.
- Если колода/комнаты нет — прежнее случайное поведение.
- Ответ — та же схема `MovieResponse`, без изменения контракта для фронта.

### 3. Наполнение колода

- Колод создаётся при первом запросе фильма в комнате (lazy): берётся перемешанная выборка из `movies` (например, до 50 id).
- При исчерпании: новая перемешанная пачка, исключая id, уже свайпнутые в этой комнате (по `user_swipes` для этой комнаты) и уже присутствующие в колоде.
- Конкурентное пополнение: операция идемпотентна (append, исключая дубли) + row lock на комнату/колод (`SELECT ... FOR UPDATE` или атомарный UPDATE), чтобы два участника одновременно не создали два колода.
- **Совместимость с `deploy-readiness`**: ротация `cleanup_old_movies` выполняется фоново; `room_decks` фильтруется по существующим id на выдаче (Requirement «Устойчивость к ротации»), поэтому удаление фильмов безопасно.

### 4. Фронтенд

- `api.ts` передаёт `room_code` (или текущую комнату) в запрос случайного фильма; `App.tsx` использует `participantIds`/`roomCode` из `GET /api/rooms/my`.
- Зависимость: фронт ожидает, что `GET /api/rooms/my` отдаёт код комнаты (уже возвращается как `room_code`). При отсутствии комнаты — случайный фильм (текущее поведение).

## Risks / Trade-offs

- **Колод на JSONB до 100 id** → запрос выбора «следующий» фильтром по массиву: в PostgreSQL индекс по `user_swipes(user_id, movie_id)` + извлечение массива на Python — приемлемо на масштабе комнат. → Ограничить размер пачки (50); при росте — перейти на таблицу `room_deck_items(room_code, position, movie_id)` с индексом.
- **Гонка при создании/пополнении колода** → два участника одновременно. → Row lock/идемпотентный append.
- **Колод и ротация фильмов** → id исчезают из базы. → Пропуск несуществующих на выдаче (Requirement зафиксирован в спеке).
- **Свайпы из прошлой «случайной» эпохи** → уже свайпнутые старые фильмы уйдут в повторы при первом колоде. → При формировании первого колода исключать фильмы, свайпнутые участником в этой комнате.

## Migration Plan

1. Аддитивная миграция: таблица `room_decks`.
2. Порядок выката: backend (миграция + endpoint) → frontend (передача `room_code`). Старая версия фронта продолжает работать со случайными фильмами (эндпоинт совместим).
3. Откат: revert backend-кода + миграция down (drop таблицы) — безопасно, т.к. таблица не критична для работы старого кода.
