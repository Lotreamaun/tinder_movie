## Context

См. proposal.md → Why. Текущая цепочка: `deck_service._grow_catalog` → `movie_service.load_batch_movies(count=MOVIES_LOAD_BATCH)` → `get_top_movies_from_kinopoisk(page)`. Последний ходит в `/api/v2.2/films/top?type=TOP_250_BEST_FILMS` и для каждого неизвестного фильма делает отдельный запрос `/api/v2.2/films/{id}` за полными данными. Уже известные фильмы пропускаются без полного запроса (Decision 7 прошлого change), поэтому проход по известной странице стоит 1 запрос.

Что проверено запросами к API 2026-09-24:
- `/films/top?type=TOP_250_BEST_FILMS`: `pagesCount = 13`, по 20 фильмов.
- `/films/collections?type=TOP_250_MOVIES`: `total = 250`, `totalPages = 13`.
- `/films/collections?type=TOP_POPULAR_MOVIES`: `total = 700`, `totalPages = 35`.
- Элементы `/films/collections` сразу содержат `kinopoiskId`, `nameRu`/`nameEn`/`nameOriginal`, `year`, `genres`, `posterUrl`, `description`, `ratingKinopoisk`/`ratingImdb`, `type`, то есть все поля, которые сейчас берутся из запроса полных данных.

Процесс один (uvicorn), догрузка идёт в одном фоновом потоке под `_growth_lock` в `deck_service`.

## Goals / Non-Goals

**Goals:**
- Догрузка находит новые фильмы, пока они есть хотя бы в одной настроенной подборке.
- Стоимость попытки в запросах квоты ограничена и предсказуема.
- Когда все подборки уже загружены, запросы к API почти прекращаются: одна проверка новинок раз в длинную паузу.
- Основная работа идёт в `movie_service`. В `deck_service` меняется только выбор длительности паузы по результату попытки.

**Non-Goals:**
- Ротация и очистка каталога (`cleanup_old_movies`, `MAX_MOVIES_IN_DB`): код фактически мёртвый в комнатном флоу, это отдельный change.
- Пауза и лок догрузки на комнату, а не на процесс.
- Компакция колоды с повторами после рецикла.
- Персистентный курсор прохода (см. Decision 3).

## Decisions

### 1. Эндпоинт подборок вместо `/films/top` и отказ от запроса полных данных

Выборка страницы идёт в `/api/v2.2/films/collections?type=<COLLECTION>&page=<N>`. Каждый элемент маппится в данные `Movie` той же логикой, что сейчас в `fetch_movie_from_kinopoisk(full_data=True)`. Эта логика (название → год → первый жанр → постер → описание → рейтинг → оригинальное название, с теми же правилами отбраковки без названия или года) выносится в одну приватную функцию маппинга. Её используют и выборка подборки, и `fetch_movie_from_kinopoisk`, чтобы правила не разъехались.

Почему: новый фильм сейчас стоит 1 + 1 запрос на каждый фильм страницы, а станет 1 запрос на страницу. Это важно при квоте в несколько сотен запросов в сутки.

Альтернатива: оставить `/films/top` и просто поднять лимит страниц. Отклонено: снимает потолок только до 250 фильмов (другие типы `/films/top` депрекейтнуты) и сохраняет дорогой запрос полных данных на каждый фильм.

### 2. Упорядоченный список подборок и бюджет страниц в `Settings`

- `KINOPOISK_COLLECTIONS: list[str]`, по умолчанию `["TOP_250_MOVIES", "TOP_POPULAR_MOVIES"]`. Можно переопределить через env строкой через запятую.
- `CATALOG_GROWTH_MAX_PAGES: int = 15`: сколько страниц максимум запрашивается за одну попытку. 15 страниц — это одна подборка `TOP_250` целиком плюс запас.

Порядок важен: сначала качественный топ, потом популярное. Тематические подборки (`FAMILY`, `LOVE_THEME` и т.п.) можно добавить конфигом без изменений кода.

Пагинация: конец подборки определяется по `totalPages` из ответа. Пустой `items` тоже считается концом подборки (защита, если `totalPages` не пришёл). Жёсткий `page > 10` удаляется.

Остановка попытки происходит по первому из условий:
- `count` — набрано `count` новых фильмов;
- `budget` — исчерпан бюджет страниц;
- `pass_end` — загружена последняя страница последней подборки. На этом попытка останавливается и не начинает новый проход в остатке бюджета, иначе вердикт «проход пуст» смешался бы со следующим проходом (Decision 6);
- `error` — ошибка запроса (сеть, 5xx, 402 квоты). Курсор не сдвигается за проблемную страницу.

Какую паузу ставить по каждой причине, описано в Decision 6.

### 3. Курсор прохода хранится в памяти процесса

`movie_service` держит состояние прохода: `(collection_index, next_page, new_in_pass)`. Попытка начинает с курсора и сохраняет место остановки, а `new_in_pass` накапливает число новых фильмов по всем попыткам текущего прохода. На `pass_end` курсор сбрасывается на `(0, 1)`, а `new_in_pass` возвращается в результате попытки и обнуляется. Доступ к состоянию сериализован уже существующим `_growth_lock`: одна догрузка на процесс. Отдельный лок не нужен, но это фиксируется комментарием.

Конец подборки: номер загруженной страницы `>= totalPages` последнего ответа или пустой `items`. `totalPages` берётся из каждого ответа заново: подборка может поменять длину между попытками.

Почему не в БД: после рестарта процесса курсор теряется, и проход начинается с первой страницы. Это стоит не больше `CATALOG_GROWTH_MAX_PAGES` дешёвых запросов (известные фильмы на странице бесплатны), после чего проход естественно доходит до новых страниц за 1–3 попытки. Таблица курсора ради этого — миграция и лишняя сущность (KISS). Так же in-memory устроены `_growth_lock` и cooldown.

Альтернатива: вычислять стартовую страницу по числу известных фильмов подборки. Отклонено: порядок подборки `TOP_POPULAR` меняется, и число известных фильмов не говорит, где лежат неизвестные.

### 4. Фильтр по типу произведения

Добавляются только элементы с `type == "FILM"`. Элементы без `type` тоже принимаются, для совместимости со старым форматом ответа. `TV_SERIES`, `MINI_SERIES`, `TV_SHOW` отбрасываются: продукт про выбор фильма на вечер.

### 5. Логирование

Одна строка INFO на страницу: `Catalog growth page collection=<C> page=<N>/<total> new=<K>`. Итоговая строка `Grew catalog by ...` в `deck_service` сохраняется. Строка «Successfully loaded 0 movies from Kinopoisk» уходит вместе со старой функцией.

### 6. Пауза по причине остановки, длинная пауза при исчерпании подборок

`load_batch_movies` возвращает не голое число, а небольшой результат (dataclass): `loaded`, `stop_reason` (`count` | `budget` | `pass_end` | `error`) и, для `pass_end`, `new_in_pass`. `deck_service._run_background_growth` выбирает паузу так:

| Причина | Пауза |
|---|---|
| `error` (и исключение в потоке) | короткая, `CATALOG_GROWTH_COOLDOWN_MINUTES` (30 мин, как сейчас) |
| `pass_end` и `new_in_pass == 0` | длинная, `CATALOG_SOURCES_EXHAUSTED_COOLDOWN_HOURS` (по умолчанию 168 = 7 дней) |
| `pass_end` и `new_in_pass > 0` | нет |
| `budget`, `count` | нет, даже при `loaded == 0` |

Механика паузы та же: одно поле `_growth_cooldown_until`, меняется только длительность. В лог пишется причина, например `Catalog growth cooldown started reason=sources_exhausted until=...`.

Почему `budget` без новых фильмов не ставит паузу: проход не закончен, и на полный проход по известным страницам (сейчас около 48 страниц, ~4 попытки) ушло бы 4 × 30 минут. Частота попыток и так ограничена естественным образом: попытка запускается только запросом фильма ниже порога и только при свободном `_growth_lock`.

После длинной паузы следующий проход проверяет новинки (в основном изменения `TOP_POPULAR_MOVIES`). Если снова пусто, ставится ещё одна длинная пауза. В установившемся режиме это один проход (~48 запросов) раз в 7 дней.

Проход, который нашёл хоть что-то, длинную паузу не ставит. Поэтому после последних найденных новинок будет ещё один проход, который и подтвердит исчерпание подборок. Это один лишний проход, и это приемлемо.

Альтернатива: отдельный флаг «подборки исчерпаны», который сбрасывается раз в N дней. Отклонено: это то же самое, что длинная пауза, но ещё одна сущность в состоянии.

## Risks / Trade-offs

- [Компромисс] Состояние прохода и паузы хранится в памяти. После рестарта (деплоя) первый же запрос ниже порога запускает новый полный проход с начала (~48 запросов, 4 попытки), даже если подборки уже исчерпаны. → Для одного процесса и редких деплоев это приемлемо. Если станет заметно, состояние можно сохранять в БД отдельным change с миграцией.

- [Риск] Формат `/films/collections` у неофициального API может измениться. → Маппинг терпим к отсутствию необязательных полей; фильмы без названия или года отбраковываются, как сейчас. Тесты фиксируют ожидаемую форму ответа.
- [Риск] 700 популярных фильмов тоже конечны. → Это отодвигает потолок примерно в 4 раза. Список подборок настраивается, так что расширение не требует кода. Полное решение (например, фильтрованный поиск `/api/v2.2/films`) в этот change не входит.
- [Риск] Рост каталога без ротации: до ~900 фильмов вместо ~200. → Для одного процесса и Postgres это несущественно. `_maybe_grow_catalog` считает `count(*)`, `_sample_movie_ids` делает `ORDER BY random()`, и оба нормально работают на тысячах строк.
- [Компромисс] Популярная подборка ниже по качеству, чем топ-250. → Она идёт второй в списке, то есть используется только когда топ исчерпан.

## Migration Plan

Меняются только код и конфиг, схема БД остаётся прежней. Выкатывается обычным деплоем backend. Первая попытка догрузки после деплоя пройдёт `TOP_250_MOVIES` (13 страниц, из них 10 бесплатно известных) и доберёт фильмы 201–250, следующие попытки перейдут на `TOP_POPULAR_MOVIES`. Когда обе подборки будут загружены, следующий проход окажется пустым, и догрузка уйдёт на 7-дневную паузу. Откат — предыдущей версией кода; загруженные фильмы остаются валидными строками `movies`.
