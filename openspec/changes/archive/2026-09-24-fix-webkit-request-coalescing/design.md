## Context

См. proposal.md — Why. Механизм и доказательства — раздел 9 в [bug-investigation.md](../fix-parallel-preload-duplicates/bug-investigation.md).

Существенно для выбора решения: **это не HTTP-кэш, а склейка одинаковых одновременных запросов в сетевом слое CFNetwork**. Экспериментально в WKWebView (5 одновременных запросов):

| Способ | Одинаковый URL | Уникальный URL |
|---|---|---|
| `XMLHttpRequest` (что использует axios) | **1 сетевой запрос, 5 одинаковых ответов** | 5 разных ответов |
| `fetch` | 5 разных ответов | — |

`Cache-Control: no-store` на ответе склейку **не отключает** — проверено. В Chrome/Chromium склейки нет (одинаковые одновременные GET сериализуются, но каждый идёт в сеть), поэтому баг видно только на WebKit-клиентах: Telegram на iPhone и macOS.

## Goals / Non-Goals

Goals:
- Два запроса «следующего фильма» никогда не совпадают побайтно, поэтому склейка невозможна ни в одном движке и ни на одном промежуточном кэше.
- Повтор фильма подряд перестаёт быть «мёртвым» нажатием — даже если дубликат всё же появится (например, из `_random_movie`-fallback).
- Фикс не зависит от внутренних деталей движка: он не «обходит WebKit», а убирает предпосылку — идентичность запросов.

Non-Goals:
- Переход axios на `fetch`-адаптер. Работает, но лечит симптом через недокументированную разницу движков и ломается при смене адаптера/полифилла.
- Изменения бэкенд-логики выдачи фильмов и схемы БД.
- Доработка `_random_movie`-fallback (исчерпание каталога) — это открытый вопрос №1 в `bug-investigation.md`, отдельная тема.

## Decisions

### D1. Уникальный одноразовый параметр в URL запроса фильма

`getRandomMovie` добавляет к URL параметр вида `_=<монотонный счётчик или uuid>`. Это делает каждый запрос уникальным, поэтому:
- сетевой слой WebKit не склеивает запросы (подтверждено экспериментом: `xhr_unique` → 5 разных ответов);
- промежуточные кэши (ngrok, CDN, корпоративные прокси) не могут отдать один ответ дважды.

Бэкенд параметр игнорирует: FastAPI не объявляет его в сигнатуре, лишние query-параметры отбрасываются — менять `api/movies.py` ради него не нужно.

Альтернативы:
- **`Cache-Control: no-store`** — не работает против склейки (проверено); оставляем как гигиену (D4), но не как фикс.
- **`fetch`-адаптер axios** — см. Non-Goals.
- **Уникальный заголовок вместо параметра** — ключ склейки строится по URL и методу, поведение по заголовкам не документировано; параметр надёжнее.

### D2. Последовательная предзагрузка вместо `Promise.all`

`initializeApp` набирает начальную очередь по одному запросу за раз. D1 уже закрывает баг, но D2 убирает саму предпосылку (одинаковые запросы в полёте), поэтому фикс переживёт, например, откат D1 или появление промежуточного кэша, игнорирующего query-параметры.

Цена по времени близка к нулю: бэкенд всё равно сериализует запросы одного участника на `FOR UPDATE` строки колоды (`deck_service`), то есть параллельные запросы и сейчас выполняются друг за другом. На время набора очереди показывается скелетон (`ui/app-bootstrap`).

Догрузка по ходу свайпов остаётся асинхронной — там одновременные запросы возможны, и их прикрывает D1.

### D3. Ключ карточки — монотонный счётчик вместо `movie.id`

`key={currentMovie.id}` + `AnimatePresence`: при совпадении id React не перемонтирует карточку и не играет exit-анимацию — нажатие визуально пропадает, хотя свайп уходит на сервер. Ключ становится счётчиком показов, который увеличивается на каждую смену карточки, поэтому повтор фильма отрабатывает как обычная смена.

Это делает фронт устойчивым к дубликатам в принципе, а не только к дубликатам из склейки: сейчас дубли ещё приходят из `_random_movie`-fallback при исчерпании каталога.

Дополнительно очередь дедуплицируется по `id` при пополнении — чтобы повтор не тратил нажатие вовсе, а не только не ломал анимацию.

### D4. `Cache-Control: no-store` на `/api/movies/random`

Не влияет на этот баг, но `GET`, который при каждом вызове возвращает разный ресурс, не должен быть кэшируемым по умолчанию. Без заголовка любой промежуточный кэш вправе переиспользовать ответ.

### D5. Флаг отмены запуска `initializeApp`

`StrictMode` в dev монтирует эффект дважды (setup → cleanup → setup), поэтому `initializeApp` выполняется два раза и два последовательных набора очереди идут параллельно: бэкенд сериализует их на `FOR UPDATE`, и каждый чейн забирает по одному фильму из каждой пары позиций колоды. Один набор затем выбрасывается, но курсор участника (`position = index + 1`, продвигается при выдаче, а не при свайпе) уже проскочил его фильмы — безвозвратно.

Для теста с несколькими участниками на dev-сервере это ломает главный сценарий: фильм должен быть показан всем участникам, чтобы матч был достижим, а каждый участник пропускает свою случайную половину первых позиций. Ожидаемое пересечение показанных фильмов у трёх участников — около одного из пяти.

Эффект получает флаг отмены: cleanup помечает запуск отменённым, а отменённый запуск выходит до цикла запросов фильмов и не пишет в state. До этого цикла есть два `await` (`getTelegramUserId`, `getMyRoom`), а cleanup вызывается синхронно сразу за первым setup, — поэтому отменённый запуск не делает ни одного запроса фильма: их снова ровно `PRELOAD_COUNT`, как в prod-сборке.

Инвариант, из которого это следует, уже зафиксирован в спеке `rooms/shared-deck` («Продвижение позиции участника по колоду»): каждый запрос продвигает позицию участника. Поэтому отдельного требования в `ui/app-bootstrap` не добавляется — оно дублировало бы уже записанное, а триггер (двойное монтирование в dev) относится к конфигурации сборки, а не к поведению продукта: в проде `App` рендерится один раз, без роутера и error boundary.

Не закрывает дрейф курсора в целом: он остаётся, когда участник закрывает miniApp с недосвайпанной очередью. Продвижение курсора по факту свайпа — отдельная тема, меняющая бэкенд-логику (см. Non-Goals).

## Risks / Trade-offs

- [Последовательная предзагрузка увеличивает время до первой карточки] → Запросы и так сериализуются блокировкой строки колоды на бэкенде; на время загрузки показывается скелетон. Если задержка окажется заметной, первую карточку можно показывать сразу после первого ответа, а остальные набирать в фоне.
- [Уникальный параметр в URL шумит в логах и полностью отключает кэширование эндпоинта] → Эндпоинт по своей природе некэшируем (каждый вызов продвигает курсор участника), терять нечего.
- [D3 меняет ключ карточки — легко «упростить» обратно при рефакторинге] → Поведение закреплено сценарием «Следующий фильм совпадает с текущим» в `ui/swipe-interaction`.
- [Баг не воспроизводится в Chrome, поэтому регрессия может вернуться незаметно] → Проверка выполняется на WebKit-клиенте (iPhone/macOS Telegram или Safari); это зафиксировано в задачах.

## Migration Plan

- Схема БД не меняется, миграции не нужны.
- Развёртывание: пересборка фронта (`npm run build`) и перезапуск uvicorn для заголовка из D4.
- Откат: revert коммита; данные не затрагиваются.
