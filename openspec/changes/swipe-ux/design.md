## Context

Текущая реализация (см. proposal.md — Why): `MovieCard.tsx` применяет transform через React state на каждый `touchmove` (ререндер всего поддерева на кадр), на карточке висит `transition-transform` (добавляет ~150ms лага за пальцем), тяжёлые `backdrop-blur` на движущейся карте. Жест — только touch-события, без `touchcancel`, регистрация только по порогу 100px без скорости. `App.tsx` блокирует все свайпы глобальным `isSwipeInProgress` на время запроса, без анимации вылета и фидбека. Старт: спиннер, мигающий баннер «Telegram ID not set», мгновенный поп-ап карточки.

## Goals / Non-Goals

**Goals:**
- 60 FPS drag с мгновенным откликом (без лага transition).
- Надёжная регистрация свайпа (дистанция ИЛИ скорость, без потерь жеста).
- Анимация вылета/входа, оптимистичный фидбек.
- Чистый старт без мигающих заглушек.

**Non-Goals:**
- Изменение визуального дизайна (glass-стиль сохраняется).
- Изменение backend API (свайп-эндпоинт не меняется; ошибки обрабатываются на клиенте).
- Общий колод фильмов — отдельный change `shared-deck`.

## Decisions

### 1. Движок анимации: framer-motion

- **Решение**: добавить `framer-motion` и переписать drag карточки на `motion.div` с `drag`, `dragConstraints`, `onDragEnd`, spring-возвратом, `exit`-анимацией вылета и `AnimatePresence` для смены карточек.
- **Почему**: framer-motion из коробки даёт 60 FPS трансформации без React-ререндера на кадр (двигает через rAF + refs), физику скорости (`info.velocity`), spring-физику возврата/вылета, exit/enter анимации. Кода на порядок меньше, чем самописный rAF-слой.
- **Альтернативы**: самописный `useRef` + `requestAnimationFrame` (полный контроль, но много кода: интеграция velocity, вылет, прерывания); `react-swipeable` (только жесты, анимацию всё равно писать вручную). Выбран framer-motion как баланс «мало кода + надёжность».

### 2. Жесты: Pointer Events + framer-motion drag

- `onPointerDown/Move/Up/Cancel` с `setPointerCapture` на карточке вместо touch-хендлеров — единая обработка мыши/тача, `pointercancel` обрабатывается как отмена с возвратом в исходное положение.
- framer-motion отдаёт скорость на `onDragEnd`; решение о свайпе: `|offset.x| > 100px` ИЛИ `|velocity.x| > 0.5 px/ms` (константы — в модуль конфигурации жеста). Направление — по знаку offset/velocity.
- Убрать `transition-transform` из класса карточки: во время драга он ломает отклик (конфликт с physics-движком); возврат/вылет делаются spring'ами framer-motion.

### 3. Оптимистичный свайп без глобальной блокировки

- Убрать глобальный `isSwipeInProgress`. При засчитанном жесте карточка сразу улетает, следующая появляется; запрос `createSwipe` идёт в фоне.
- Ошибка отправки: не откатывать карточку (сложно и сбивает ритм), а показывать неблокирующий баннер/уведомление с текстом ошибки; последующие свайпы разрешены. (Серверная идемпотентность `user+movie+group` уже защищает от дублей при повторах.)
- **Альтернатива**: возврат карточки на ошибке — отброшено: риск дублей и рывков, а ошибка сети редко значит потерю данных для следующей карточки.

### 4. Старт приложения

- **Идентификация**: дождаться инициализации `window.Telegram.WebApp` (проверять `initData`; при необходимости — короткий retry/таймаут), баннер «Telegram ID not set» показывать только если SDK по-настоящему не дал личность, а не до разрешения инициализации.
- **Скелетон**: заменить спиннер на скелетон карточки (прямоугольник постера + плейсхолдеры текста) с `animate-pulse`.
- **Enter-анимация**: первая карточка — через framer-motion `initial/animate` (scale-in). Постер следующей карточки предзагружается через `new Image()` до показа.
- **Поздняя загрузка постера**: карточка получает `aspect-ratio` постера заранее (или фиксированную высоту), чтобы подгруз не дёргал layout.

### 5. Перфоманс на движущейся карте

- `will-change: transform` на карточке, `contain: layout paint`.
- Тяжёлые `backdrop-blur` (`backdrop-blur-[40px]` на info-панели, `backdrop-blur-xl` на кнопках) на движущейся карточке заменить на дешёвые градиенты/полупрозрачные подложки (градиент уже есть) — blur оставить только на статичных элементах (MatchOverlay) или `backdrop-blur-sm`.
- Проверить профилем DevTools Performance на реальном устройстве (спринт-репро, задача ниже).

### 6. Спринт-репро «5-й попытки»

- Гипотезы, которые проверяются на устройстве в Telegram: (a) потеря жеста через `touchcancel`, (b) тихая блокировка на время медленного запроса, (c) фидбек не виден, т.к. нет анимации вылета. Фиксируется фактический триггер и результат (видео/логи), чтобы подтвердить связь с задачами 1–4.

## Risks / Trade-offs

- **Размер бандла framer-motion** (~50 kB gzip) → приемлемо для мини-аппа; при критичности можно заменить на самописный rAF-слой (интерфейс жеста изолируется в хук `useSwipeGesture`).
- **Оптимистичный свайп при ошибке сети** → свайп «ушёл», но не сохранился на сервере. → Баннер ошибки + идемпотентность на сервере; ретрай доступен повторным свайпом.
- **Тонкая настройка velocity** → зависит от устройства. → Константы вынесены в один модуль, подбираются в спринт-репро.
- **`contain: paint` + `overflow-hidden` на карточке** могут срезать тень/блик → проверить визуально в репро.

## Migration Plan

1. Инкрементально, только фронтенд: (1) framer-motion + переписанная MovieCard, (2) оптимистичный flow в App.tsx, (3) bootstrap/старт, (4) перфоманс-проход.
2. Без изменения контракта API — откат = revert коммитов фронтенда.
