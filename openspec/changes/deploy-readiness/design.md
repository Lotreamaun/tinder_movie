## Context

Текущее состояние (см. proposal.md — Why): FastAPI с синхронным SQLAlchemy, идентификация через доверяемый клиентский заголовок `telegram-id`, бот на polling в отдельном процессе, нет Docker/CI. Известные баги: сломанный форматтер логов (конкатенация строк-литералов в `logging_config.py`), троекратный `check_match` в `create_swipe`, `is_notified=true` сразу после спавна потока, `leave_room` кидает исключение для последнего участника, синхронные вызовы Kinopoisk в пути запроса `get_random_movie`.

Ключевые факты, влияющие на дизайн:
- Все эндпоинты — синхронные `def`, FastAPI исполняет их в threadpool → синхронный SQLAlchemy не блокирует event loop.
- Бот и API — отдельные процессы.
- `SECRET_KEY`/`JWT_SECRET` объявлены, но нигде не используются.

## Goals / Non-Goals

**Goals:**
- Валидация личности через Telegram initData вместо доверенного заголовка.
- Полная контейнеризация и CI/CD, миграции при деплое.
- Устранение блокирующих багов и ненадёжных фоновых операций.
- Rate limiting на API.

**Non-Goals:**
- Масштабирование на несколько инстансов (в памяти rate limit, один инстанс бота).
- Переход на async SQLAlchemy (не требуется — threadpool уже изолирует event loop).
- Новые продуктовые фичи (общий колод фильмов — отдельный change `shared-deck`).
- Тюнинг производительности сверх снятия блокеров.

## Decisions

### 1. Аутентификация: валидация Telegram initData

- Валидация по официальному алгоритму Telegram: секретный ключ = `HMAC_SHA256(bot_token, "WebAppData")`, затем `HMAC_SHA256(secret_key, data_check_string)`; сравнение с полем `hash` — constant-time.
- `auth_date` — порог свежести (например, 24 часа), `user.id` обязателен.
- FastAPI-зависимость `get_current_user(init_data: str = Header("X-Telegram-Init-Data"))` → объект пользователя; защищённые роутеры (swipes, rooms, matches) используют её. Заголовок `telegram-id` удаляется из контракта.
- **Альтернативы**: собственный JWT (не нужно — Telegram уже даёт стабильную личность, а `JWT_SECRET` сейчас мёртвый код); OAuth2 (избыточно). Решение: использовать initData; мёртвые `SECRET_KEY`/`JWT_SECRET` из конфига удалить.

### 2. Фронтенд: передача initData

- `frontend/src/services/api.ts` берёт `window.Telegram.WebApp.initData` и кладёт в заголовок `X-Telegram-Init-Data` вместо ручного `telegram-id`.
- Dev-режим: в обычном браузере initData нет — dev-фоллбэк (`VITE_DEV_TELEGRAM_ID`) остаётся только под `import.meta.env.DEV`, в проде запрос без initData → 401.

### 3. Надёжные уведомления: outbox + воркер

- **Проблема**: сейчас thread + новый event loop на каждый матч; `is_notified=true` ставится авансом; при падении процесса уведомление теряется.
- **Решение**: таблица `match_notifications` (outbox): `id`, `match_id`, `status` (pending/sent/failed), `attempts`, `next_attempt_at`, `error`. Создание матча пишет строку outbox. Фоновый воркер (в процессе бота, который и так живёт постоянно) забирает pending-задачи, отправляет через Telegram Bot API, на успехе — `status=sent` + `match.is_notified=true`; на ошибке — `attempts+1`, `next_attempt_at` с backoff.
- **Альтернативы**: `BackgroundTasks` FastAPI (теряются при рестарте, живут в API-процессе); Celery (избыточно). Outbox — простой, устойчивый к рестартам, совместим с отдельным процессом бота.

### 4. Kinopoisk вне пути запроса

- Фоновый планировщик (простая asyncio-задача/thread в API-процессе, запускается при старте) периодически проверяет `count(movies)`, при падении ниже порога догружает батч.
- `get_random_movie` никогда не вызывает Kinopoisk: если база пуста — возвращает 404 (фронт показывает состояние), фоновый наполнятель наполняет.
- Ротацию/чистку старых фильмов (`cleanup_old_movies`) тоже убрать из пути запроса и выполнять в том же фоновом цикле. (Взаимодействие с `shared-deck` учитывается: колод фильтруется по существующим id.)
- **Альтернативы**: cron-скрипт (доп. инфраструктура); наполнение при старте (недостаточно для длинной сессии). Выбран фоновый цикл с интервалом.

### 5. Прочие баги

- **Форматтер логов**: убрать сцепку строк-литералов в `logging_config.py`; формат — одна строка.
- **`check_match`**: в `create_swipe` выполнять проверку один раз и возвращать результат; убрать дубли.
- **`leave_room`**: для последнего участника — возвращать штатный результат (комната удалена), не бросать `ValueError`.
- **Rate limit**: `slowapi` (in-memory) с лимитом на identity+IP; для одного инстанса достаточно. Redis — отложенная опция при горизонтальном масштабировании.
- **Конфигурация**: строгие pydantic-настройки; обязательные переменные проверяются при старте; удалить секреты-заглушки.

### 6. Деплой

- **Docker**: мультистейджи. Backend: python:3.12-slim, non-root, установка из `requirements.txt`, entrypoint `alembic upgrade head && uvicorn app.main:app`. Frontend: `node` build → `nginx` (static + proxy `/api`). `.dockerignore` для обоих.
- **docker-compose**: `db` (postgres:16, volume, healthcheck), `api` (healthcheck, depends_on db healthy, env), `bot` (запуск `run_bot.py`, single replica), `frontend` (nginx, exposes 80).
- **Bot**: остаётся на polling в отдельном контейнере с гарантией одного инстанса (replicas=1) для MVP. Webhook — задокументированный вариант миграции (нужен публичный HTTPS-адрес); в дизайн закладывается константа `WEBHOOK_URL`-путь, но не реализуется в этом change.
- **CI**: GitHub Actions workflow — lint (ruff), тесты (pytest, backend), build (tsc, frontend), сборка обоих образов, публикация в registry (шаг, включаемый по env). Секреты — GitHub secrets.

## Risks / Trade-offs

- **initData в обычном браузере** → 401 в проде (мини-апп должен открываться внутри Telegram). → Миграция: dev-фоллбэк только под `import.meta.env.DEV`; UX-ошибка 401 с понятным сообщением «откройте через Telegram».
- **Outbox-воркер живёт в процессе бота** → если бот лежит, уведомления задерживаются. → Ретраи с backoff + логирование ошибок; при разворачивании отдельного воркер-контейнера перенос кода тривиален.
- **Фоновый наполнятель и rate limit Kinopoisk** → ключ API может упереться в лимит. → Backoff при 429, дедупликация, интервал больше порога догрузки.
- **In-memory rate limit** → не общий между инстансами. → Приемлемо для одного инстанса; документирован переход на Redis.
- **Миграция auth-контракта** → фронт и бэкенд деплоятся согласованно, иначе свайпы отвалятся. → Выкатывать вместе; старый заголовок не поддерживается (сознательная ломка, задокументирована).

## Migration Plan

1. Порядок: (a) backend-фиксы надёжности, (b) auth-контракт backend, (c) frontend-передача initData, (d) Docker/compose/CI, (e) миграция БД (таблица outbox — аддитивная, без разрушительных изменений).
2. Пункты (b)+(c) выкатываются одновременно, т.к. меняют контракт API.
3. Откат: передеплой предыдущих образов (compose хранит теги); outbox-таблица аддитивна, её наличие не мешает старой версии кода.
