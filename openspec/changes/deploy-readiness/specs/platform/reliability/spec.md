## Purpose

Повышение надёжности backend: корректные логи, отсутствие блокирующих внешних вызовов в HTTP-пути запроса, гарантированная доставка уведомлений о матчах и защита API от злоупотреблений.

## ADDED Requirements

### Requirement: Корректный формат логов

Все записи логов SHALL иметь единый структурированный формат (время, имя логгера, уровень, сообщение) без постороннего префикса.

#### Scenario: Формат записи лога
- **WHEN** приложение записывает лог
- **THEN** строка начинается с времени в формате `%Y-%m-%d %H:%M:%S` и не содержит служебных текстовых блоков из конфигурации форматтера

### Requirement: Уведомления о матчах с подтверждением доставки

Флаг `is_notified` у матча SHALL устанавливаться только после фактически успешной отправки уведомлений всем участникам. Неуспешные отправки SHALL помечаться как ожидающие доставки и повторяться.

#### Scenario: Успешная отправка
- **WHEN** уведомление о матче успешно доставлено участникам
- **THEN** матч помечается `is_notified = true`

#### Scenario: Ошибка отправки
- **WHEN** отправка уведомления завершилась ошибкой
- **THEN** матч остаётся `is_notified = false` и доставка повторяется позже

### Requirement: Внешние вызовы вне пути HTTP-запроса

Загрузка и ротация фильмов из Kinopoisk API SHALL выполняться в фоновых задачах, а не в пути HTTP-запроса. Обработка запроса случайного фильма SHALL не блокироваться сетевыми вызовами к внешнему API.

#### Scenario: Запрос фильма при пустой базе
- **WHEN** пользователь запрашивает случайный фильм, а в базе фильмов мало
- **THEN** ответ не ожидает обращения к Kinopoisk API; наполнение базы выполняется фоново

#### Scenario: Сбой внешнего API
- **WHEN** Kinopoisk API недоступен
- **THEN** HTTP-запросы пользователей продолжают обслуживаться, а фоновое наполнение повторяет попытки с задержкой

### Requirement: Однократная проверка матча при свайпе

Обработка одного свайпа SHALL выполнять проверку совпадения (match) не более одного раза.

#### Scenario: Свайп-лайк
- **WHEN** пользователь ставит лайк фильму
- **THEN** сервер выполняет проверку матча один раз и возвращает её результат в ответе

### Requirement: Ограничение частоты запросов API

API SHALL ограничивать частоту запросов для защиты от злоупотреблений. При превышении лимита SHALL возвращаться HTTP 429.

#### Scenario: Превышение лимита
- **WHEN** клиент превышает допустимое количество запросов за период
- **THEN** API возвращает HTTP 429 с указанием времени до сброса лимита

#### Scenario: В пределах лимита
- **WHEN** количество запросов в пределах лимита
- **THEN** запросы обрабатываются штатно без HTTP 429

### Requirement: Выход последнего участника — штатный сценарий

Выход последнего участника из комнаты SHALL обрабатываться как нормальная операция (комната удаляется), а не как ошибка.

#### Scenario: Последний участник выходит
- **WHEN** последний участник выходит из комнаты
- **THEN** комната удаляется, и клиент получает корректный результат без ошибки
