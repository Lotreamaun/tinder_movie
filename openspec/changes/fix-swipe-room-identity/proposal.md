## Why

Свайп сегодня идентифицируется не комнатой, а **снимком состава участников на момент свайпа**: `user_swipes.group_participants` (JSONB-массив `telegram_id`) входит в уникальный ключ `uq_swipe_user_movie_group`, а все выборки «свайпы этой группы» идут через JSONB-оператор `@>` (contains). Оператор несимметричен, поэтому при любом изменении состава комнаты (кто-то присоединился или вышел — штатный флоу, см. change `notify-room-join`) идентичность свайпа «плывёт»:

- **Состав вырос → дубль голоса.** Есть строка с `[1,2]`, приходит свайп с `[1,2,3]`: проверка `[1,2] @> [1,2,3]` = false, `swipe_service.get_swipe` существующий свайп не находит, уникальный ключ дубль не ловит (наборы-то разные) — создаётся вторая строка. У пользователя по одному фильму лежат **лайк в `[1,2]` и дизлайк в `[1,2,3]` одновременно**.
- **Состав сжался → перезаписывается чужая строка.** Есть строка с `[1,2,3]`, приходит свайп с `[1,2]`: containment true → `get_swipe` находит строку **старого** состава и перезаписывает её `swipe_type`/`swiped_at`, а свайпа для текущего состава `[1,2]` не появляется вовсе.
- **`check_match` и `/api/matches/vote-status` считают неверно.** Они фильтруют тем же `@>`, поэтому для группы `[1,2]` совпадут обе строки — и устаревший лайк из `[1,2]` засчитается как голос, хотя актуальный вердикт пользователя дизлайк. Возможен ложный матч.
- **Пятисотки.** `get_swipe` завершается `scalar_one_or_none()`: как только по одному `(user, movie)` есть две строки, подходящие под containment, запрос падает с `MultipleResultsFound`, и каждый следующий свайп по этому фильму отдаёт HTTP 500.
- **Свайпы чужой комнаты выжимают каталог.** Тот же `@>` в `deck_service._swiped_movie_ids` захватывает группы-надмножества: свайпы из другой комнаты с теми же участниками исключают фильмы в текущей. Уже задокументировано (`fix-parallel-preload-duplicates/bug-investigation.md`, разделы 3, 4.2, 8 п.3) и отложено — этот change его закрывает.

Сценарий полностью достижим на проде: `frontend/src/App.tsx:139-142` читает `participantIds` один раз при инициализации и больше не обновляет, так что клиент какое-то время шлёт устаревший состав, а после перезагрузки — новый.

Продуктовое требование при этом однозначно: **голос сохраняется при смене состава комнаты и аннулируется только по окончании сессии комнаты** (скользящее окно 24ч, уже введённое change `fix-movie-catalog-exhaustion`). Значит снимок состава — неверный носитель идентичности; идентичность должна давать комната.

## What Changes

- **BREAKING (схема БД).** `user_swipes` и `matches` получают колонку `room_code` (FK на `rooms.id`). Уникальные ключи переезжают на неё: `uq_swipe_user_movie_room (user_id, movie_id, room_code)` вместо `uq_swipe_user_movie_group`, `uq_match_movie_room (movie_id, room_code)` вместо `uq_match_movie_group`. `group_participants` сохраняется как исторический снимок «кто был в комнате на момент свайпа/матча», но перестаёт участвовать в идентичности и в выборках.
- Все выборки «свайпы этой комнаты» (`swipe_service.get_swipe`/`check_match`, `deck_service._swiped_movie_ids`/`_swiped_movie_ids_in_room`, `room_session.get_session_start`, `/api/matches/vote-status`, `match_service.check_existing_match`/`list_matches_for_group`) переходят с `group_participants @>` на `room_code = :room_code` + фильтр по сессии. Оператор `@>` по составу участников уходит из кода свайпов и матчей полностью.
- **Голос переживает смену состава.** Свайп, сделанный в комнате до присоединения/выхода участника, остаётся тем же голосом: `get_swipe` находит его по `(user, movie, room)` и обновляет, а не создаёт второй. Лайк и дизлайк одного фильма одним участником в одной комнате одновременно становятся невозможны физически (уникальный ключ).
- **Матч считается по актуальному составу комнаты.** `check_match` требует лайк от всех текущих участников комнаты в рамках текущей сессии; лайки, поставленные до смены состава, засчитываются (не аннулируются). Матч по одному фильму в одной комнате создаётся один раз — повторное уведомление при смене состава исключено.
- **BREAKING (API).** `room_code` определяется на сервере по `telegram_id` (`room_service.get_user_current_room`), а не берётся из тела запроса: клиентский `group_participants` больше не влияет на идентичность свайпа, что снимает проблему устаревшего состава на фронте. `POST /api/swipes/` при отсутствии активной комнаты отвечает 400. `GET /api/matches/?participants=…` и `GET /api/matches/vote-status?participants=…` переходят на параметр `room_code` (текущих потребителей у этих ручек нет — ни фронтенд, ни бот их не вызывают).
- Гонка на вставке свайпа устраняется: check-then-insert в `create_swipe` заменяется на `INSERT ... ON CONFLICT (user_id, movie_id, room_code) DO UPDATE`, так что двойной тап или ретрай больше не приводит к `IntegrityError` → HTTP 500.

## Capabilities

### New Capabilities
- `rooms/swipe-identity`: принадлежность свайпа комнате и идемпотентность голоса — один участник имеет по одному фильму не более одного голоса в комнате, повторный свайп перезаписывает предыдущий, смена состава участников голос не удваивает и не аннулирует, матч по фильму в комнате создаётся один раз.

### Modified Capabilities
- `rooms/shared-deck`: требование «Сессия комнаты сбрасывает просвайпанность» перепривязывается с «группы участников» на **комнату** — сессия считается по свайпам комнаты (`room_code`), а не по свайпам состава через `@>`. Требование «Отсутствие повторов для участника» уточняется: исключаются только свайпы этой комнаты в текущей сессии, свайпы из других комнат (в т.ч. с тем же или более широким составом) фильмы больше не исключают. Требование «Совпадение матча в комнате» уточняется: матч проверяется по актуальному составу комнаты, лайки из того же сеанса до смены состава засчитываются.

## Impact

- **Схема БД**: новая Alembic-миграция в `backend/app/migrations/versions/` — `room_code` в `user_swipes` и `matches`, смена уникальных ключей, индексы по `room_code`. Бэкфилл существующих строк — см. design.md (сессии живут 24ч, поэтому исторические строки на поведение почти не влияют).
- `backend/app/models/swipe.py`, `backend/app/models/match.py` — новая колонка, новые `UniqueConstraint`/`Index`, обновлённые докстринги.
- `backend/app/services/swipe_service.py` — `get_swipe`, `create_swipe` (upsert), `check_match`; `_group_contains` удаляется.
- `backend/app/services/match_service.py` — `check_existing_match`, `create_match`, `list_matches_for_group`; `_group_contains` удаляется.
- `backend/app/services/room_session.py` — `get_session_start` принимает `room_code` вместо `participants`.
- `backend/app/services/deck_service.py` — `_swiped_movie_ids`, `_swiped_movie_ids_in_room` (фильтр по `room_code`).
- `backend/app/api/swipes.py` — серверное определение комнаты, 400 без активной комнаты, устранение двойного вызова `check_match` в ответе.
- `backend/app/api/matches.py`, `backend/app/api/schemas.py` — `room_code` вместо `participants` в ручках матчей и в `SwipeCreate`/`SwipeResponse`.
- `frontend/src/services/api.ts`, `frontend/src/App.tsx` — `createSwipe` шлёт `roomCode` вместо `groupParticipants`; исчезает зависимость свайпа от закешированного состава участников.
- `backend/tests/` — новый `test_swipe_identity.py` (смена состава, идемпотентность, гонка, отсутствие ложного матча), правки `test_shared_deck.py` под новую сигнатуру сессии.
